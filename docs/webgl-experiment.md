# Эксперимент: real-time WebGL вместо Blender-пролётов

> Разделы до «Вторая художественная итерация» описывают первую итерацию. Архитектура, профили качества, debug-панель и бенчмарк не изменились; изменилась мегаструктура (`world.ts`) — см. последний раздел.

Ветка `experiment/realtime-webgl` (от `main` @ `21ae506`). `main` не тронут, рендеры и последовательности кадров на месте.

## Как запустить

```sh
npm install
npm run dev                 # http://localhost:4321/It-was-just-like-a-movie/
```

| URL-параметр | Что делает |
|---|---|
| (нет) | WebGL-сцена (по умолчанию в этой ветке) |
| `?engine=legacy` | исходные Blender-пролёты (`SequenceStage`), без изменений |
| `?quality=low\|medium\|high` | зафиксировать профиль качества (запоминается в `localStorage`) |
| `?debug=1` | панель диагностики + переключатель качества (`auto` сбрасывает ручной выбор) |

Бенчмарк (нужен production-сервер на порту 4390 и установленный Chrome):

```sh
npm run build
npm run preview -- --port 4390
npm run bench:webgl                       # dGPU (если Chrome выберет его), 40 с скролла
npm run bench:webgl -- --igpu             # встроенная графика
npm run bench:webgl -- --igpu --cpu 4     # CPU замедлен в 4 раза (слабый ноутбук / телефон)
npm run bench:webgl -- --igpu --throttle  # сеть 20 Мбит/с, 40 мс
npm run bench:webgl -- --shots            # скриншоты всех сцен обоих движков → docs/perf/shots
```

Результаты: `docs/perf/*.json`, скриншоты: `docs/perf/shots/`.

## Исходная архитектура (с чем сравниваем)

- Один fixed `<canvas>` 2D (`src/scripts/sequence.ts`, `SequenceStage`) рисует покадровые пролёты с cover-кадрированием 16:9 и кросс-фейдом соседних кадров.
- 5 пролётов: `approach` (90 кадров), `f_stories`, `f_subjects`, `f_formats`, `f_final` (по 72). Четыре тира разрешения (960 WebP/AVIF, 1920/2560/3840 AVIF) — 302 МБ на диске, около 40 МБ на тир 960 и около 50 МБ на тир 1920.
- `src/scripts/journey.ts` — ScrollTrigger на каждую сцену. Каждый трек вызывает `stage.show(sequence, t)`, `stage.setFade()`, ставит `--construction` и анимирует DOM. Сцена держит последний кадр своего пролёта как фон.
- Маршрут камеры (по последним кадрам):
  1. **Hero → approach**: сфера справа сверху, Земля слева снизу, станция на стреле → сфера анфас по центру (фон сцены 02, «Истории»; чертёж — отдельные DOM-слои `public/blueprint`, к кадру не привязаны).
  2. **f_stories → Маршрут (03)**: близко над оболочкой, через кадр идёт кольцо.
  3. **f_subjects → Предметы (04)**: общий план сверху.
  4. **Автор (05)**: собственного пролёта нет; затемнение, затем статичный кадр «окно капсулы» (`public/scenes/pod_interior_comp*.webp`).
  5. **f_formats → Форматы (06)**: над северным полюсом, радиаторная корона, кольца над головой.
  6. **f_final → Контакт (07)**: обратно к кадру hero, сфера достроена.
- `boot.ts` держит первый экран в темноте, пока не придут кадры `approach`.
- На телефонах (≤900px) пролёты не скрабятся: показывается только последний кадр сцены.
- Весь контент, формы, отзывы, табы, лайтбокс и навигация — DOM. От кадров зависят только фон и «construction».

## Новая архитектура

```
journey.ts ──(тот же API: show / setFade / setFocus / toScreen / progress / onFrameLoad)──► WebGLStage
                                                                                      │
                                    src/scripts/webgl/stage.ts  ◄─────────────────────┘
                                      ├─ один WebGLRenderer, одна сцена, одна камера на всё время жизни
                                      ├─ «последовательность» = путь камеры (CatmullRom centripetal, по длине дуги)
                                      ├─ cover-crop 16:9 через camera.setViewOffset — композиция совпадает с кадрами
                                      ├─ профили качества, бенчмарк, адаптивное разрешение, пауза на скрытой вкладке
                                      └─ world.ts: процедурная мегаструктура
```

Ключевое решение: `WebGLStage` реализует тот же интерфейс, что и `SequenceStage`. Поэтому `journey.ts` изменился на ~15 строк: выбор движка, `setConstruction`, подключение debug-панели. Бизнес-логика, ScrollTrigger-сценарии, формы и разметка не тронуты. `boot.ts` теперь принимает любой объект с `progress()`/`onFrameLoad()`. Legacy-движок доступен через `?engine=legacy`. Он же — автоматический fallback, если WebGL2-контекст не создаётся.

**Детерминизм.** Состояние сцены — чистая функция от (путь, t, construction). Обратный скролл приводит к тому же кадру. Сглаживание камеры — та же экспоненциальная догонялка к цели, что была у скраббера кадров, независимая от частоты обновления. Накопительных анимаций нет. От времени зависит только «фоновая жизнь»: орбиты роя, огни на кольцах, вращение Земли, мерцание звёзд. При `prefers-reduced-motion` время заморожено, кадры рисуются только по изменению.

### Мегаструктура (`world.ts`)

| Элемент | Реализация | Draw calls |
|---|---|---|
| Звезда | сфера 64×32, fbm-грануляция, потемнение к краю | 1 |
| Свечение | billboard без depth test (дешёвый «bloom»), гаснет по мере закрытия оболочки и вблизи корпуса | 1 |
| Оболочка коллекторов | `InstancedMesh` панелей по широтным рядам (2.4k / 6.5k / 13k). Изнутри освещены звездой, снаружи — «зеркальная» мозаика с разбросом нормалей | 1 |
| Несущий каркас | `LineSegments` меридианов и параллелей | 1 |
| Термопояс | открытый цилиндр, сетка панелей в шейдере, «наматывается» с construction | 1 |
| Полярные короны | `InstancedMesh` радиаторных лопастей, 48 шт | 1 |
| Статиты-зеркала | `InstancedMesh` шестиугольников внутри оболочки | 1 |
| 4 сервисных кольца | torus + шейдер: латунные муфты, бегущие огни; внешнее кольцо растёт с construction | 4 |
| Спицы колец | `InstancedMesh` цилиндров | 1 |
| 3 стрелы-фермы | `InstancedMesh` коробок, решётка фермы — `discard` в шейдере | 1 |
| Станции (хаб + 2 колеса) | 2 × `InstancedMesh` | 2 |
| Свободный рой | `InstancedMesh` (1.2k / 3.5k / 8k), орбиты считаются **в вершинном шейдере** (CPU = 0); дальние панели не меньше пикселя, яркость — по реальному покрытию | 1 |
| Земля + атмосфера | fbm-континенты, города вдоль побережий, подсветка «из-за планеты» как на рендере | 2 |
| Звёздное небо | `Points` (2.5k–8k), треть звёзд — в галактической полосе, едет вместе с камерой | 1 |

Итого **≈18 draw calls**, 70–85k треугольников на high. Текстур нет: всё процедурное, 0 байт ассетов.

**Строительство (`constructionProgress` 0→1)** — *итерация 1; во второй итерации заменено активацией светом (см. последний раздел).* Всё, что появляется со временем, — `InstancedMesh`, где инстансы заранее отсортированы по моменту появления (`aRank`). Обновление = `mesh.count` (бинарный поиск) + один uniform: невидимые инстансы GPU даже не обрабатывает, а свежие плавно масштабируются из нуля в шейдере. Оболочка растёт от экватора неровными пятнами, внешнее кольцо и спицы — по дуге, пояс наматывается, короны собираются по лопастям, рой густеет, свечение звезды гаснет, когда оболочка закрывается. Значения construction те же, что в исходном сценарии (0.42 → 1). Аллокаций в кадре нет.

**Композиция.** Ключевые ракурсы (`K` в `stage.ts`) подобраны по последним кадрам Blender-пролётов. Земля и первая стрела не заданы координатами, а вычисляются из кадра hero (`anchors()`): unproject точки кадра, где они стоят на рендере. Так композиция первого экрана держится при правке камеры.

### Качество и производительность

- **Профили** `low / medium / high`: число панелей, роя, звёзд и статитов, сегментация колец и Земли, октавы шума, диапазон разрешения рендера. На low MSAA выключен.
- **Автовыбор**: устройства с touch или Data Saver стартуют на low. Остальные — короткий бенчмарк реальной сцены на первом кадре: 5 кадров, `readPixels` как синхронизация, то есть время GPU без vsync. Порог <4 мс → high, <11 мс → medium, иначе low. Результат кэшируется в `localStorage` по имени GPU, повторный визит бенчмарк не гоняет. Ни user-agent, ни число ядер не используются.
- **Адаптивное разрешение**: EMA времени кадра. Выше 21 мс разрешение снижается шагом 0.15, поднимается осторожно (не раньше 10 с после замедления). Если на минимальном разрешении 3 с подряд медленно (и качество не выбрано вручную), профиль понижается. Пересборка мира ждёт, пока камера остановится, чтобы не дёрнуть пролёт.
- **Энергия**: без движения камеры 2 с — фоновая жизнь рисуется на половинной частоте. Скрытая вкладка — rAF остановлен. Полная темнота (затемнение сцены «Автор») — рендер пропускается. `powerPreference: "default"`: браузер сам выбирает GPU, ноутбук не будит дискретную видеокарту ради сайта.
- Шейдеры компилируются через `compileAsync` (параллельно, где драйвер умеет).

### Панель `?debug=1`

FPS (текущий и средний), время кадра (среднее и p95), draw calls, треугольники, линии, точки, активные инстансы, профиль и причина выбора, масштаб рендера, сцена, путь и t, construction, число геометрий и текстур, JS heap (если браузер даёт), имя GPU. **Время GPU и VRAM не показываются**: timer query в WebGL ненадёжен, а VRAM браузер не отдаёт. Выдумывать эти числа панель не будет.

## Измерения

Условия: production-сборка (`astro preview`), Chrome (headed, реальный GPU), окно 1440×900, DPR 1, кэш выключен, у каждого движка свежий профиль браузера (первый визит). Сценарий: загрузка → 1.5 с паузы → **40 с равномерного скролла от начала до конца страницы** (`scrollTo` в каждом rAF). Сравнение идёт на одной сборке: `?engine=legacy` против WebGL по умолчанию. Legacy при этом тоже скачивает бандл с Three.js; разница в JS вынесена в таблицу отдельно, по сборке `main`.

**Железо:** ноутбук, AMD Ryzen AI 7 350, 32 ГБ RAM, два GPU: AMD Radeon 860M (встроенная) и NVIDIA GeForce RTX 5060 Laptop. **Экран 144 Гц** (кадр 6.9 мс), поэтому потолок FPS — 144, а не 60. Какой GPU реально рисовал, записано в каждом JSON (`gpu`). Без флагов Chrome выбрал RTX 5060, с `--igpu` — Radeon 860M. Один прогон на конфигурацию: разброс между повторами не измерялся. Ранние прогоны во время разработки давали те же порядки.

|---|---|---|---|---|
| RTX 5060 | legacy | **1.11 с** | **1.34 с** | **98 мс** |
| RTX 5060 | webgl | 1.45 с | 1.44 с | 246 мс |

| сеть 20 Мбит/с | webgl | 1.83 с | **1.82 с** | 149 мс |

Здесь WebGL **хуже**. На локальной сети первый полезный кадр приходит на 0.1–0.2 с позже, FCP — на 0.25–0.9 с позже, а main thread при старте заблокирован дольше: парсинг 650 КБ JS, сборка мира, компиляция шейдеров, бенчмарк качества. Профиль старта показал, что почти всё это нативная работа браузера («(program)»), а не JS движка. При первом визите мир собирается дважды (стартовый профиль → профиль по замеру); повторный визит берёт результат из `localStorage`, в бенчмарке это не отражено. Через реальную сеть (20 Мбит/с) WebGL готов **на 1.1 с раньше**: он не ждёт 3.4 МБ кадров. «Время до интерактивности» здесь приравнено к снятию вуали (до него контент `inert`). Это не стандартная метрика TTI.

### Память

JS heap: legacy 3.2–3.9 МБ, WebGL 6–8.8 МБ. **Это сравнение некорректно**, выводы из него делать не стоит. Декодированные кадры legacy (до сотен МБ bitmap в процессе рендера и на GPU) в JS heap не попадают, а память GPU/VRAM браузер не отдаёт. Я её не измерял. По устройству WebGL держит одну сцену без текстур: несколько МБ вершинных и инстансных буферов плюс framebuffer. Legacy держит декодированные кадры 1920×1080 (~8 МБ каждый) в кэше изображений. Это оценка из конструкции, а не измерение.

### Что дороже всего в WebGL

GPU-таймеры не использовались, по элементам я не профилировал. Ниже — ранжирование по устройству шейдеров, **не измерение**:

1. **Fill rate крупных по площади поверхностей**: billboard свечения звезды (аддитивный, без depth test) и шейдер Земли (fbm на каждый пиксель, 3–5 октав). Поэтому разрешение рендера и октавы шума — первые рычаги профилей.
2. **Оболочка коллекторов**: до 13k инстансов с фрагментным шейдером отражения. Плотность — второй рычаг.
3. **CPU**: не рендер (≈18 draw calls, позиции роя считаются на GPU), а старт: парсинг Three.js, сборка мира, компиляция шейдеров.

**Главный ограничитель** — не GPU: на испытанном железе даже встроенная графика упирается в vsync 144 Гц. Ограничивают главный поток при загрузке и, на слабых CPU, общий код страницы при скролле.

## Что удалось и что нет

**Удалось**
- Весь сценарий из 7 сцен работает на WebGL с тем же маршрутом и функциями сцен. Тексты, CTA, отзывы, табы, лайтбокс, форма, навигация, мобильная раскладка и reduced-motion не тронуты (`npm run verify` проходит, ошибок в консоли нет).
- Ракурсы всех пяти пролётов воспроизведены по их конечным кадрам. Движение между ними непрерывное и детерминированное, вперёд и назад одинаково.
- Процедурное строительство 0.42 → 1 полностью на GPU-буферах: оболочка, кольцо, спицы, пояс, короны, рой, гаснущее свечение. Финальная сцена показывает почти законченную сферу.
- Профили качества с автовыбором по замеру, ручное переключение, адаптивное разрешение, debug-панель, воспроизводимый бенчмарк.
- Плавность на всех испытанных конфигурациях заметно лучше legacy.

**Не удалось / хуже оригинала**
- **Фотореализм и плотность деталей.** Blender-сфера — это тысячи уникальных деталей: модули, капсулы, тарелки, фермы со светом, мягкие тени, объёмное свечение. Процедурная — честная стилизация. На дальних планах (hero, финал, общий план) она убедительна. Вблизи (сцены 03 и 06) видно, что это повторяющиеся панели, а не инженерная конструкция. Моя оценка: композиция и масштаб — 8/10, материал и детализация — 4–5/10.
- Нет теней и настоящего bloom. Сделано сознательно: это самые дорогие эффекты, а цель — слабые устройства.
- Земля процедурная: континенты не похожи на реальные, огни городов местами «блочные» (value noise).
- Окно капсулы в сцене «Автор» осталось пререндеренной картинкой. Это неподвижный кадр, а не пролёт; гибрид допустим.
- Старт тяжелее: +131 КБ gzip JS, FCP позже, больше blocking time при загрузке.
- Потеря контекста WebGL (`webglcontextlost`) не обрабатывается: при сбросе драйвера фон замрёт до перезагрузки.
- На телефоне проверены только эмуляция (390×844, touch → low), отображение и отсутствие ошибок. FPS на реальном телефоне **не измерялся**.

## Рекомендации

- **Перевести на WebGL**: hero и финал (ключевой визуальный выигрыш; «строительство» в реальном времени кадры не умеют), подход к сфере (approach) и общий план (f_subjects). Это дальние планы: стилизация там близка к рендеру, а вес падает с десятков МБ до нуля.
- **Оставить Blender или гибрид**: близкие пролёты над оболочкой (f_stories → сцена 03) и над полюсом (f_formats → сцена 06), где решает детализация, и окно капсулы. Напрашивающийся гибрид: WebGL для движения камеры и дальних слоёв плюс один пререндеренный ключевой кадр для близкой сцены — несколько МБ вместо 70.
- **Если продолжать**: (1) обработать `webglcontextlost` с откатом на legacy; (2) собирать мир после первого кадра страницы (`requestIdleCallback`) — это вернёт FCP; (3) 5–10 GLB-деталей (станции, модули, тарелки) поверх процедурной оболочки — главный путь к детализации без потери скорости; (4) замерить на реальном телефоне и слабом ноутбуке с одной встроенной графикой.

## Независимая оценка

Гипотеза подтвердилась **частично**.

**По весу и плавности эксперимент удался однозначно.** Данных за визит в 24 раза меньше (67.8 → 2.8 МБ). Рывки при скролле исчезли: p99 7 мс против 49 мс, 0 long tasks против 50. На медленной сети сайт готов на секунду раньше. Встроенная графика ноутбука выдаёт полные 144 кадра в секунду. Это измеренные числа, но по одному прогону на одной машине.

**По визуалу — нет, если мерить фотореализмом Blender.** Процедурная сфера масштабна и узнаваема и на дальних планах держит величественность. На близких планах она проигрывает рендеру по материалу и количеству уникальных деталей. Посетитель, видевший оба варианта, разницу заметит. Тот, кто видит только WebGL, вероятно, нет.

**Цена, которую легко недооценить**: старт стал тяжелее по CPU (+131 КБ JS, FCP позже). Каждое изменение сцены теперь — шейдерный код, а не рендер в Blender: поддержка требует graphics-программиста, а не 3D-художника.

**Вывод:** продолжать стоит в гибридном виде. WebGL — основа пролётов и дальних планов, для близких сцен — несколько пререндеренных ключевых кадров или GLB-детали. Отказываться от Blender полностью я бы не стал. От 300 МБ покадровых пролётов — стоит.

# Вторая художественная итерация

Задача: не трогая архитектуру и производительность, уйти от неудачного псевдо-реализма к стилизованной орбитальной мегаструктуре. Сделать панели объёмными, пояса осмысленными и убрать «достройку на глазах». Всё изменение — в `src/scripts/webgl/world.ts` плюс выбор варианта в `stage.ts`.

## Что изменено и почему

**1. Достройка убрана (вариант A).** Сфера существует сразу. Ни один инстанс больше не появляется: `aRank`, сортировка по рангу и `mesh.count` по прогрессу удалены. Значение `construction` из сценария сайта теперь — только *активация* (`uLive`, плавно 0.42 → 1). Она усиливает свет в швах, свечение рёбер модулей и неоновые линии колец. Ничего не спавнится; к финалу структура насыщается светом, а не деталями.

**2. Панели получили объём.** Каждая панель — тонкий бокс (толщина 0.035–0.06, посадка по высоте ±0.005), а не плоскость. Верх в шейдере:
- скошенная рамка (bevel): нормаль у края наклоняется к ближайшей кромке, поэтому у каждой панели есть освещённое и затенённое ребро под фиксированным холодным key-светом;
- утопленная пластина внутри рамки, разделённая тонкими канавками на ячейки;
- редкие светящиеся вставки (тёплые и cyan, около 1%).

Стенки — тёмный металл, подсвеченный снизу светом из швов: в ближних пролётах видно, что панель стоит над светящейся щелью. Плиты намеренно тёмные; свет живёт на фасках, на краю сферы и в швах.

**3. Свет из-под оболочки вместо звезды.** Под панелями — одна сфера «света звезды», её показывают швы. Белая там, где взгляд идёт прямо к звезде, cyan вокруг, фиолетовая у лимба, медленно дышит. Звезда с fbm-грануляцией удалена: за полной оболочкой её не видно. Bloom стал примерно втрое слабее и лежит только над самым горячим местом.

**4. Две шкалы порядка.** Главная находка итерации: каждый 30° меридиан и каждый 16-й ряд оставлены открытыми. Свет рисует по сфере крупную сетку секторов, внутри — мелкая панельная кладка. Ряды выровнены по 12 секторам, поэтому каналы идут ровно. Сфера читается как спроектированный объект с любой дистанции: издалека — светящаяся сетка, вблизи — канал между стенами панелей.

**5. Инженерные модули.** Поверх кладки — редкие (1/70 от числа панелей) плоские крупные модули с рядами огней. Экваториальный пояс стал кольцом объёмных фиолетовых модулей с портами, полярные короны — объёмными лопастями. Всё рисуется тем же материалом панели, новых шейдеров нет.

**6. Кольца — меньше, но сильнее.** Вместо четырёх колец со спицами и пробных дуг — экваториальное сервисное кольцо, два наклонных и одна большая незамкнутая дуга (200°) как композиционный жест. Металл темнее; вдоль внешней стороны трубы идёт тонкая неоновая линия с бегущими импульсами, её яркость растёт с активацией. Спицы только у двух внутренних колец.

**7. Орбитальные потоки — модули логистики.** Вместо плоских квадратиков — объёмные боксы-контейнеры, ориентированные по движению: длинная ось вдоль орбиты, у каждого лёгкий крен. Тёмный корпус освещается светом оболочки со стороны звезды, рёбра светятся cyan. Дальние модули не меньше пикселя и тускнеют по реальному покрытию. Около 6% модулей идут короткими конвоями по 4–10 «нос к хвосту», поэтому поток читается как транспортная система, а не как пыль.

## Сравнение вариантов

Все варианты остались в коде и включаются параметрами `?shell=hybrid|refined|layered` и `?swarm=ribbon|modules|shards` (первый — по умолчанию). Сравнение — на пяти одинаковых ракурсах (hero, близко над оболочкой, полюс, общий план, финал), UI скрыт: `docs/perf/shots/compare-shells.jpg`, `docs/perf/shots/compare-swarms.jpg`.

**Оболочка**

| Вариант | Что это | Итог |
|---|---|---|
| refined | объёмные панели, узкие тёмные швы, без крупных модулей | Спокойно и благородно вблизи, но издалека — однородный «шар из плитки», нет иерархии. |
| layered | внешняя кожа с регулярными окнами на слой крупных внутренних модулей | Интересно в ближнем плане, но на дальнем окна превращаются в шум, сфера теряет силуэт. |
| **hybrid** (выбран) | объёмные панели + светящиеся швы + сетка световых каналов + редкие модули | Читается на всех дистанциях, даёт две шкалы порядка и «звезду внутри» без псевдо-реализма. |

Промежуточные шаги hybrid: (1) толстые крупные блоки (0.12–0.28) выглядели как кубики конструктора — заменены плоскими модулями; (2) каналы через каждые 15° давали слишком дробную, «молниеобразную» сетку (ряды были сдвинуты) — стало 30° с выровненными рядами.

**Орбитальные потоки**

| Вариант | Что это | Итог |
|---|---|---|
| ribbon (первая версия) | 75% модулей в длинных конвоях + светящиеся трассы орбит | Системно, но добавляло ещё десяток линий к и без того линейной сцене — получались каракули. Трассы удалены. |
| modules | объёмные контейнеры, равномерно по 9 орбитальным плоскостям | Лучший ритм и глубина, хорошо читается на среднем плане. |
| shards | гранёные пластинки, более рыхлое облако | Изящно вблизи, но на дальнем плане почти исчезает. |
| **ribbon** (итог, выбран) | modules + короткие конвои по 4–10 модулей | Ритм modules плюс читаемая функция — транспортные потоки. |

## Цена по производительности

Тот же стенд и сценарий: 1440×900, 40 с скролла, экран 144 Гц, по одному прогону.

| | Итерация 1 | Итерация 2 |
|---|---|---|
| Draw calls | ≈18 | **18** |
| Треугольники (high / medium / low) | ≈84k на high | 231k / 134k / 64k |
| Инстансы (high) | 9–22k, росли с construction | 14.5k, постоянно |
| RTX 5060: avg FPS / p99 кадра | 143.3 / 7.1 мс | **143.0 / 7.1 мс** |
| Radeon 860M: avg FPS / p99 кадра | 142.6 / 7.5 мс | **140.3 / 13.9 мс** |
| Radeon 860M + CPU в 4 раза медленнее: avg FPS / кадров >50 мс / TBT скролла | 81.4 / 15 / 176 мс | **81.2 / 13 / 96 мс** |
| Long tasks при скролле (без замедления CPU) | 0 | **0** |
| Данные за визит | 2.79 МБ | **2.79 МБ** |

Треугольников стало в 2.7 раза больше: панели и модули теперь боксы по 12 треугольников. На FPS это почти не влияет — draw calls те же, а часть фрагментной работы исчезла (fbm-звезда, слой линий каркаса). Единственный заметный сдвиг — p99 на встроенной графике: 7.5 → 13.9 мс, то есть 1% кадров идёт через кадр на 144 Гц; средний FPS тот же. Прогон с замедленным CPU повторён: первый совпал с общим замедлением машины (legacy в нём тоже упал с 66 до 44 FPS), в таблице — повторный.

## Компромиссы

- **Прямые углы.** Панели — боксы без настоящей фаски: на лимбе и в ближнем пролёте видны прямые углы. Настоящий bevel — +60% треугольников; оставлено так.
- **Линии.** Даже после чистки сцена линейно насыщена: кольца, дуга, фермы, потоки. Дальше упрощать стоит после реакции на живую прокрутку.
- **Свет «изнутри» — стилизация.** Физически полная сфера Дайсона снаружи тёмная; швы светятся, потому что так читается «звезда внутри».
- **Земля не менялась**: процедурные огни городов местами блочные, только приглушены.
- **Варианты оставлены в коде** ради повторного сравнения (несколько десятков строк). Если выбор окончательный, `refined`, `layered`, `modules` и `shards` можно удалить.

## Задел для Saturn-концепта

Ничего не реализовано, но архитектура не мешает. Мир строится одной функцией `buildWorld(tier, layout, look)`, а камера и сценарий от неё не зависят. Новый концепт — ещё один `look` (или второй `buildWorld`) на тех же путях камеры; кольца, потоки модулей и материал панелей переиспользуются как есть.
